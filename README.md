# 결제 통로를 클라이언트가 고르게 두면 생기는 일 — Claude "Cassia" 신뢰경계 취약점 분석

> Anthropic Claude 결제 플로우(`checkout_capabilities`)를 사례로, "클라이언트가 결제 통로를 고르게 만든" 신뢰경계(trust boundary) 취약점 클래스를 해부하고 방어를 설계한다.

**⚠️ 상태**: 본 리포에서 다루는 구체적 이슈는 **이미 패치됨**. 이 저장소는 공격 재현 도구가 아니라 **취약점 클래스 분석 + 방어 레퍼런스**다. 실제 서비스를 대상으로 한 결제 우회 코드, 가짜 IBAN 생성기, 계정 대량 생성 파이프라인은 포함하지 않는다.

원 분석 글: [caowo.de — 焚决 Claude](https://blog.caowo.de/posts/claude-cassia-mock-payment-bypass-analysis/)

## TL;DR

- **근본 원인**: 서버가 "이 사용자가 어떤 결제 통로를 쓸지"라는 **정책 결정**을, 클라이언트가 임의로 바꿀 수 있는 API 응답 필드(`checkout_flow`)에 위임했다.
- **증폭 요인**: SEPA 직접출금(Direct Debit)은 제출 시점에 계좌 실재성을 검증하지 않고 T+1~3영업일 뒤에 청산된다. 즉 **"서비스 개통"이 "결제 확정"보다 먼저** 일어나는 비동기 확인 공백이 존재한다.
- **결과**: 결정 필드 하나를 동기 확인이 강한 통로(카드)에서 비동기 확인 통로(은행출금)로 바꾸면, 확인 공백 동안 유료 기능이 활성화된다.
- **핵심 교훈**: 이건 특정 버그가 아니라 **"클라이언트가 조작 가능한 상태가 서버의 가치 결정을 좌우한다"**는 재사용 가능한 취약점 패턴이다.

## 이 저장소에 없는 것 (의도적으로)

- 실제 claude.ai(혹은 다른 실서비스) 결제를 우회하는 동작 스크립트
- 유효한 IBAN을 대량 생성해 실제 결제망에 밀어넣는 코드
- 계정 팜 / 자동화 세션 관리 노하우

데모는 전부 `localhost`에서 뜨는 가짜 결제 서버만 대상으로 하며, 어떤 실제 결제망과도 통신하지 않는다.

## 빠른 시작 (데모)

```bash
cd demo
node vulnerable-server.js      # 취약 구현: 클라이언트가 보낸 flow를 신뢰
# 다른 터미널에서
node attack-client.js          # 로컬 취약 서버에 flow 위조 요청 → 개통됨(취약)

node fixed-server.js           # 수정 구현: 서버가 flow를 자체 결정 + 비동기결제 지연개통
node attack-client.js --port 3001   # 동일 공격 → 거부됨(안전)
```
